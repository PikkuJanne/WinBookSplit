## Work

Audit runtime syntax, standard-library/native usage and upstream security/lifecycle/distribution sources for Python 3.11–3.14. Define one versioned production policy and a separate build/test lock. Document per-branch floors, advisory versus blocking reasons, prerequisites and actual test targets. Evaluate all four candidate minors; no exclusions merely to avoid work. At least two minors must survive actual testing before release. Do not ship the unresolved policy template.

## Acceptance

- **V101-AC-006:** All four candidate branches evaluated with concrete inclusion/exclusion reasons; security and Windows binary availability reviewed.
- **V101-AC-007:** One validated policy design is used across setup/probe/PowerShell validation/tests/docs; exact build pins are separate.
- **V101-AC-008:** Later stable maintenance versions inside approved branches are accepted without exact equality or a live online check.
- **V101-AC-009:** Each hard floor/exclusion has applicable evidence; recommended latest patch is not silently used as an equality/minimum rule.
- **V101-AC-010:** Only tested regular stable x64 CPython branches are advertised; 32-bit, ARM, free-threaded and future untested minors are excluded clearly.

## Checkpoint and continuation
Record actual commands, source/package identity, outcomes and limitations in a brief redacted evidence file under `evidence/`. Update TASKS/ACCEPTANCE_CASES/STATUS/NEXT_SESSION. Commit only intended files, push normally and verify clean HEAD against the freshly queried live remote branch. A prior receipt does not certify a later commit. Then continue the next ready task rather than asking the owner to approve another ordinary milestone.

No private documents, fabricated evidence, unapproved infrastructure or destructive Git commands. Human testing is governed by HUMAN_TESTING.md, not the old v1.0.0 checklist. If this task is genuinely blocked, identify the exact dependency and complete independent work first.
